形成的核心分工是：

- `README.md`：项目介绍、入口、安装和运行方式；
- `AGENTS.md`：Codex 的工作约束、验证要求和阅读路由；
- `docs/product.md`：产品问题、用户、范围、流程和非目标；
- `docs/architecture.md`：模块边界、依赖关系、数据流和技术选择；
- 其他 `docs/` 文件只在对应信息确实复杂时创建；
- 子目录只有在存在不同命令、边界、风险或团队规则时才建立嵌套 `AGENTS.md`。

## 四、Skill 初版完成后的说明

Skill 名称：`bootstrap-codex-project`。

原始个人安装位置：

```text
C:\Users\JIE\.codex\skills\bootstrap-codex-project
```

它包含三层语义：

1. 项目事实：`README.md`、`docs/`、代码、测试和决策记录；
2. Codex 指导：根或必要的嵌套 `AGENTS.md`；
3. 可选能力：`.codex/`、`.agents/skills/`、MCP、Rules、Hooks、自定义 Agent 和定时任务。

它支持 Greenfield、Existing repository、Audit/refresh 三种模式，以及 Minimal、Standard、Advanced 三档输出。高级表面从不因为“完整”而自动生成。

完成过的验证包括：

- 官方 `quick_validate.py`；
- 两个 Python 脚本语法检查；
- 仓库检查器和上下文验证器的正向、负向测试；
- 本地链接、占位符、个人路径、密钥模式、嵌套规则和高级表面检查。

## 六、新会话是否需要重新调用

用户：

> 换新会话需要重新调用skill吗？

结论：不需要每次都调用。

- 项目已经整理好后，新会话进入项目时会自动读取项目里的 `AGENTS.md`；
- 普通开发不必重新调用 Skill；
- README、架构、命令或目录明显变化时，再调用 Skill 做审计或刷新；
- 新会话不会继承旧聊天内容，所以事实必须保存在项目文件中；
- 显式写 `$bootstrap-codex-project` 最可靠，也可以让 Codex 根据描述自动匹配。

## 七、完整文件体系

用户：

> 只有这几个吗？README.md：项目介绍、入口和运行方式 AGENTS.md：Codex 工作约束 docs/product.md：产品范围 docs/architecture.md：架构边界

不是只有这几个。它们是核心文件，不是固定清单。

| 文件或目录 | 负责什么 | 什么时候需要 |
| --- | --- | --- |
| `README.md` | 项目是什么、如何启动、文档入口 | 几乎所有项目 |
| `AGENTS.md` | Codex 的工作规则、验证要求 | 几乎所有项目 |
| `docs/INDEX.md` | 文档导航 | 文档超过两三个时 |
| `docs/product.md` | 用户、问题、流程、范围、非目标 | 产品型项目 |
| `docs/architecture.md` | 模块职责、依赖边界、数据流、技术选择 | 多模块项目 |
| `docs/data-model.md` | 实体、关系、不变量、敏感数据 | 有数据库或复杂业务对象时 |
| `docs/glossary.md` | 专有名词和准确含义 | 术语容易混淆时 |
| `docs/testing.md` | 测试层级和发布门槛 | 测试方式较复杂时 |
| `docs/operations.md` | 部署、配置、监控、备份和恢复 | 长期运行或上线时 |
| `docs/decisions/` | 长期技术决策和替代方案 | 有重要架构决策时 |
| `docs/work/current.md` | 当前进度和临时问题 | 长项目跨会话工作时 |
| `PLANS.md` | 多阶段任务计划契约 | 高风险长任务 |
| 子目录 `AGENTS.md` | 局部规则 | 子目录有真实差异时 |

高级能力包括 `.codex/config.toml`、`.agents/skills/`、`.codex/rules/`、`.codex/hooks.json`、`.codex/agents/`、MCP 和 Automation，但都不是默认必需品。

## 九、持续开发、反赶工与自我辩论

用户：

> 假设我在做一个项目已经计划好了，想让codex一直开发不中途停下，还有一个目的是解决codex赶工/偷懒/以为完成某个它自认为的内定标准就是完成任务的缺点，我之前用这段话作为项目目标进行引导：自行辩论下一步的最优任务进行处理，处理后进行自我辩论，辩论是否有遗漏/急功近利，自行辩论任务路线是否有跑偏，辩论得出结论后按结论进行下一步。我的这句话语义标准吗？有歧义吗？如何修改更好？有其他更好的方式能解决这个情况吗？能否开发成技能？技能的方式更好还是我的方式更好？

这段话表达了正确担忧，但“最优任务”“自我辩论”“是否完成”和“继续到什么时候”都没有可观察标准。模型可能仍然自行选择任务、自行降低完成门槛，或者把一次反思当成新的完成证据。

更可靠的方式不是增加更长的“不要偷懒”提示，而是建立执行闭环：读取有权限的活动计划、声明本轮预期与验证、实现边界清晰的增量、运行真实检查、对照验收条件审查遗漏和跑偏、记录证据与下一步，只在达到明确终止条件或遇到真实阻塞时停止。

自我审查有价值，但它必须围绕验收条件、测试结果、实际界面或行为和未解决风险展开；冗长的内部辩论不能代替这些证据。这个机制适合做成 Skill，因为 Skill 可以把普通用户的自然语言目标翻译成计划、边界、验收、验证和交接规则，而不要求用户每次手写完整流程。

## 十、短期计划与长期路线冲突

用户：

> 可是短期plan有时不能按照长期plan的计划走时怎么办？有时我希望先完善某个功能，这和我的长期plan冲突

临时优先级可以偏离长期路线，但必须把“改变执行顺序”和“改变项目终点”分开：

- 当前想先完成的功能成为活动计划或其中的当前任务；
- 原长期任务记录为暂停或延后，保留原因、影响、恢复条件；
- 产品范围、架构、安全和数据兼容性边界不会因普通调序而静默改变；
- 当前功能完成后必须明确等待、恢复某个任务或激活另一个计划。

用户：

> 可是codex经常把短期plan和长期plan混淆，我让它按当前计划走，结果它跑去执行长期计划

问题根源不是计划内容不够多，而是多个文件看起来同时具有执行权。因此形成计划权限模型：

```text
docs/roadmap.md          长期方向，execution_authority: none
PLANS.md                 唯一活动执行计划，status: active，authority: exclusive
docs/work/current.md     进度和交接，execution_authority: none
AGENTS.md                每个会话都会读取的路由和冲突规则
```

Codex 不得从路线图、README、普通 Todo、归档计划或进度记录自行挑选下一任务；活动计划被阻塞时也不得偷偷切换到长期路线。完成后只执行活动计划中明确的 `wait`、`resume:<task-id>` 或 `activate:<plan-id>`。

用户：

> 你刚才写的技能考虑到这个了吗？需不需要更新？

结论是需要更新。初版虽然区分长期计划和当前工作，但没有把执行权限、冲突优先级、临时调序、完成去向和机械校验定义得足够严格。本次更新据此增加了条件启用的计划权限模块、模板、迁移规则和验证器。

## 十一、普通用户与 Skill 的真正价值

用户：

> 普通用户根本不会想到那么细，不会拥有那么成熟的标准化流程。而大公司老开发者对这些的需求性并不是太高，因为他们形成习惯和标准流程了。所以你要求所有用户都按照你的严格模式走根本不现实。而这时候skills的重要性就来了。普通用户按照引导走，而不需要搞懂我要写哪些规则，哪些规则怎么写是正确的...而这样子做的话，skills的重要性和要应对局面的复杂性就加大了，因为每个人遇到的情况问题都不同。所以skills需要尽量全面，减少特殊情况的尴尬境地。评估我这段话

这段判断成立，而且指出了 Skill 设计最容易犯的错误：把专家流程直接暴露给普通用户。普通用户不应先理解 `AGENTS.md`、计划权限、验收契约、Hook 或 MCP 才能得到专业结果；Skill 应通过少量白话问题和仓库证据，在内部完成这些判断。

同时，“尽量全面”不能等于给所有项目生成最多文件、问最多问题或启用最严格流程。更准确的定义是：

> 全面的是 Skill 的判断能力，不是它给每个项目生成的文件数量。

Skill 内部应覆盖常见风险、冲突和异常路径，外部入口保持简单；复杂模块按证据渐进启用。无法确定时应区分 `Open` 与 `Assumed`，采用可逆的低风险默认值，或在涉及数据、架构、安全和外部权限时交还用户决策。

成熟团队并非没有价值：Skill 可以把隐性经验变成可复用规则，减少项目间漂移，帮助新人进入项目并自动检查文档、规则和计划冲突，但不应强迫专家重复基础访谈。

## 十二、面向未来 Skill 的设计准则

用户：

> 把我们讨论的这段话蒸馏成.md文件，我要作为将来开发其他skills时给智能体看，让它明白skills需要具备什么

本请求形成了 [`references/skill-design-principles.md`](../references/skill-design-principles.md)。它不是某个项目必须复制的模板，而是维护和设计其他 Skill 时供智能体读取的准则，包含：

- 自然语言入口和普通用户假设；
- Skill 作为翻译器、顾问而非模板复制器；
- 内部判断全面、外部输出克制；
- 渐进式披露与少量关键问题；
- Verified、Decided、Planned、Assumed、Open 证据状态；
- 长期路线、活动计划和进度记录分权；
- 临时优先级、暂停、恢复和完成去向；
- 用测试、CI、Hook 或验证脚本承接机械约束；
- 防止局部完成被误判为整体完成；
- 对无法覆盖的特殊情况安全降级。

## 十四、中途要求应该修改哪一层

用户：

> 我中途如果提要求，bootstrap-codex-project 技能懂得如何更改吗？会自动判断这个要求是修改长期路线，还是短期支线，还是临时修改呢？

结论是：Skill 应该自动判断，但不能假装所有情况都能无歧义推断。用户不需要学习计划术语；Skill 根据实际影响把要求分为三类：

- `task_adjustment`：仍属于当前目标，只改变实现方法、界面文案、局部行为或验收细节；
- `priority_branch`：暂时暂停当前任务，先完成另一个明确目标，但长期终点不变；
- `roadmap_change`：改变长期产品范围、非目标、架构、安全、数据兼容性、支持平台或项目终点。

如果不同解释会改变长期边界或完成后的恢复行为，Skill 只问一个白话问题。例如：“做完后要回到刚才暂停的任务，还是停下来让你检查？”可逆、局部、低风险的不确定性可以记录假设后继续；涉及架构、安全、数据和外部行为时不能擅自假设。

## 十五、新任务和子代理如何跟随规则

用户：

> 那你开始进行补充，以及主代理如果为了当前项目开新会话子代理时，规则需不需要跟随，怎么跟随，你也一并考虑。都补充好以后同步更新github。github更新不只是更新代码，使用说明也要同步更新

这里必须区分持久仓库规则与当前任务上下文：

```text
AGENTS.md               每次在仓库中运行时发现的持久规则
PLANS.md                当前唯一活动执行权限
docs/work/current.md    跨任务的进度、证据和下一动作
主代理的委派消息       子代理当前这次工作专用的有限任务包
```

新任务会重新发现适用的 `AGENTS.md`，但不会继承旧聊天里没有写入仓库的决定。分叉会复制分叉点之前的聊天，但分叉之后两边的新进展不会互相自动同步。子代理虽然能读取仓库规则，也不能自动知道当前目标、用户最新要求、排除范围、验收条件和返回格式。

因此主代理必须给子代理明确提供：

```text
task_id
objective
requirement_change_class
allowed_scope
excluded_scope
authoritative_files
acceptance_criteria
validation
write_policy
repository_state
side_effects_policy
escalation
expected_return
```

普通子代理不得修改长期路线、改变活动计划的执行权限、重新分类用户要求、扩大范围、选择无关路线图任务或宣布整个项目完成；普通任务包也不能转授这些权限。主代理负责检查实际差异和证据、运行集成验证、处理冲突并更新交接状态。

如果新 Codex 任务不是协助而是正式接管，还必须交接仓库和工作树位置、分支、基准提交、未提交改动、最新用户决定、下一动作、责任类型和最终汇报归属。只有正式 `take_over` 才把本次用户请求的集成和汇报责任交给新任务；“整个项目完成”仍是更高层级、需要独立验收标准的判断。

本次补充同步修改 Skill 主流程、计划规则、用户访谈、Codex 表面指南、Skill 设计准则、活动计划模板、进度模板、`AGENTS.md` 模板、子代理任务包、验证器、测试和 README 使用说明。
