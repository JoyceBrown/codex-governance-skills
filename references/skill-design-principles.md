# Skill 设计准则

这份文档用于指导未来设计 Codex Skill 的智能体。它描述的是设计原则，不是某个具体 Skill 的实现步骤。

## 核心定义

Skill 的价值不是保存一段更长的提示词，也不是要求用户先学会专业流程。

Skill 应该把用户的自然语言目标、仓库事实和当前工作环境，转换成适合当前项目的可执行工作流、文档结构、规则和验证方式。

用户只需要说明想做什么、当前最关心什么以及不能接受什么；Skill 负责判断需要哪些文件、规则、问题、工具和检查。

## 用户假设

### 普通用户

普通用户通常不会预先知道：

- `README.md`、`AGENTS.md`、`PLANS.md` 和 Skill 分别负责什么；
- 产品范围、架构边界、完成标准和验证证据应该如何表达；
- 长期路线和当前任务冲突时应该如何记录；
- 什么时候应该使用规则、Hook、CI、MCP、自动化或额外的 Agent。

Skill 不应要求用户先掌握这些概念。应通过少量、白话、真正影响结果的问题，替用户完成专业翻译。

### 熟练开发者和成熟团队

熟练用户可能已有流程，但 Skill 仍然可以帮助：

- 把隐性经验变成团队可复用的显性规则；
- 减少不同项目和成员之间的流程差异；
- 让新人更快进入项目；
- 自动执行重复的检查、记录和交付步骤；
- 发现规则漂移、文档过时和计划冲突。

Skill 不应假设专家什么都不需要，也不应强迫专家重复基础访谈。

## 设计总原则

### 1. 全面的是判断能力，不是输出文件数量

Skill 应全面覆盖常见决策类型、风险和异常情况，但只生成当前项目真正需要的内容。

不要把“全面”理解成：

- 每个项目都生成完整文档树；
- 每个项目都启用高级配置、Hook、MCP、自动化或多 Agent；
- 让用户回答大量只有专家才理解的问题；
- 把所有可能的特殊情况都写成强制规则。

正确目标是：内部判断能力全面，用户入口简单，生成结果克制，复杂能力按证据逐步启用。

### 2. Skill 是翻译器和顾问，不是模板复制器

Skill 应完成以下转换：

```text
自然语言目标
    -> 项目事实和未知项
    -> 风险与复杂度判断
    -> 最小必要的上下文结构
    -> 可执行规则和验证方式
```

不要仅根据项目名称、依赖名称或用户的一句描述猜测架构、命令、目录或技术选型。

### 3. 渐进式披露

默认只解释和生成最小结构。只有在发现明确需求时，才启用更复杂的模块。

建议按以下顺序处理：

1. 读取用户目标和现有仓库证据。
2. 判断项目规模、风险和持续时间。
3. 询问最多几个会改变结果的关键问题。
4. 选择最小、标准或高级配置档案。
5. 生成并验证结果。
6. 把复杂决策记录下来，而不是把复杂概念全部转嫁给用户。

可逆的问题应采用明确标注的合理默认值；不可逆、涉及产品方向、数据、安全、外部权限或高成本迁移的问题必须询问。

### 4. 对不确定性诚实

事实、用户决策、计划、假设和未解决问题必须区分。Skill 不应把计划写成已经实现，也不应把模型推断写成项目事实。

建议至少使用以下证据状态：

- `Verified`：已由仓库证据或成功命令验证；
- `Decided`：用户或权威项目决策明确指定；
- `Planned`：已接受但尚未实现；
- `Assumed`：为了继续工作而采用的可逆假设；
- `Open`：尚未解决或存在冲突。

### 5. 让机械工具负责机械约束

提示词适合表达目标、判断和工作方式；测试、类型检查、lint、CI、Hook 和验证脚本适合阻止可以机械识别的错误。

不要只要求模型“不要偷懒”。应尽量把完成标准转换成可执行检查和可审查证据。

## 长项目和计划冲突

不是每个项目都需要计划权限模型。只有当项目存在长期路线、当前焦点、跨会话工作或计划混淆风险时，才启用它。

启用后，必须区分：

```text
长期路线：说明最终方向，不直接授权执行
活动计划：当前唯一具有执行权的计划
进度记录：记录已完成、失败、风险和交接信息
```

建议结构：

```text
docs/roadmap.md          长期方向，仅供参考
PLANS.md                 唯一活动执行计划
docs/work/current.md     进度和跨会话交接记录
AGENTS.md                规定执行权限和冲突处理
```

如果用户临时要求先完善某个功能：

1. 将它作为当前活动计划或活动计划中的明确任务；
2. 记录被暂停的长期任务、原因、影响和恢复条件；
3. 不修改长期终点，除非用户明确改变产品、架构、安全或兼容性约束；
4. 当前任务完成后，按照明确的 `on_complete` 行为恢复、切换或等待；
5. 不得自行从长期路线选择下一项任务。

活动计划至少应明确：

```text
plan_id
status
current_task_id
allowed_scope
excluded_scope
deferred_work
on_complete
validation
```

不要让两个文件都包含没有权限标记的可执行待办列表。长期路线中的复选框、模糊的“下一步”和多个未标记的活动计划，都会增加 Codex 误选任务的概率。

## 持续开发与反赶工

“持续开发”不等于无限运行，也不等于永远不向用户报告问题。Skill 应要求 Codex 在满足终止条件前不要主动宣布完成，但必须允许真实阻塞、权限缺失、外部决策和环境故障正常中断。

每个执行循环应包含：

1. 读取活动计划和已有证据；
2. 选择活动计划允许范围内的最高价值未完成任务；
3. 在修改前定义预期结果和验证方法；
4. 实现一个边界清晰的增量；
5. 运行适用的测试、构建、检查或实际行为验证；
6. 对照验收条件检查遗漏、跑偏、临时方案、回归和未记录假设；
7. 记录证据、失败、风险、决策和下一任务；
8. 只有达到终止条件或真实阻塞时才停止。

不得用以下内容代替完成：

- 代码已经写出来；
- 页面可以打开；
- 一个局部测试通过；
- 任务看起来复杂；
- 已经完成了一轮总结；
- 模型自我判断“应该够了”。

自我审查应当对照验收条件和实际证据，而不是要求模型进行冗长的“自我辩论”。

## 适应不同用户和项目

Skill 应根据证据调整强度：

### Minimal

适合小型、早期或低风险项目。通常只需要项目介绍、启动方式、基本规则和验证命令。

### Standard

适合多模块、有测试、有持续开发需求的软件。增加产品范围、架构边界、验证方式、决策记录和必要的当前计划。

### Advanced

只有在用户或仓库明确需要时，才增加计划权限、Hook、规则、MCP、自动化、自定义 Agent 或更严格的交付门槛。

选择高级模式不应成为用户的前置知识要求，而应是 Skill 根据风险和工作方式作出的解释性决策。

## Skill 的容错设计

Skill 不可能预先穷尽每个人的所有情况，因此需要优先保证优雅降级：

- 无法确认时标记为 `Open` 或 `Assumed`，不要伪造确定性；
- 不确定但可逆时采用低风险默认值并告知用户；
- 可能破坏数据、范围、架构或外部权限时停止并询问；
- 发现现有文件时保留其意图，不要为了套模板覆盖；
- 发现冲突时指出权威来源和冲突内容，而不是擅自折中；
- 复杂结构没有实际收益时主动简化；
- 当前流程未覆盖某个情况时，给出安全的人工接管点。

## 设计检查清单

开发或维护 Skill 前，检查：

- 用户是否可以只用自然语言开始？
- Skill 是否能从仓库事实中补足常见信息？
- 是否只询问会改变结果的问题？
- 是否根据项目证据选择复杂度，而不是默认生成全部能力？
- 每条重要规则是否有明确的权威位置？
- 是否区分事实、决策、计划、假设和未知？
- 是否存在多个文件同时拥有任务执行权？
- 当前计划和长期路线冲突时是否有清晰处理方式？
- 完成标准是否包含验证证据？
- 是否有防止局部完成被误判为整体完成的检查？
- 是否允许用户临时改变优先级？
- 是否记录暂停、恢复和放弃的任务？
- 是否能在复杂情况无法判断时优雅降级？
- 是否避免把专家流程强制施加给简单项目？
- 是否把可机械执行的要求交给测试、CI、Hook 或脚本？

## 给未来开发 Skill 的智能体

设计 Skill 时，优先追求以下结果：

> 让不懂流程的用户也能得到专业结果，让懂流程的用户不必重复基础流程；内部判断要全面，用户入口要简单，输出结构要最小，关键结论要有证据，复杂能力要按需启用，计划偏差要可记录，任务完成要可验证，无法判断时要安全降级。
