# 项目审议分析（deliberate-project）

一个面向 Codex 的证据驱动项目审议技能。它通过三个基础审理者，结合动态选择的审理角度、推导方式、专业知识、证据比对和验证手段，发现具体软件、产品、技术或工程项目中容易被单一路径遗漏的细节、关系、矛盾、风险、机会和竞争性判断。

中文自然语言调用口令：`三堂会审`

内部技能标识：`deliberate-project`

系统显式调用：`$deliberate-project`

## 大白话说明

它不是让三个人举手表决，而是让项目接受多种不同检查：

- 有人专门拆假设、找反例和失败条件。
- 有人专门补关系、补场景、补利益相关者和长期影响。
- 有人按当前领域的真实标准、工程实践和验证手段检查。
- 主代理再根据项目特征选择第一性原理、因果链、反事实、系统关系、生命周期、对标、威胁建模、人因、运维韧性、敏感性分析等不同审法。
- 证据还要比较权威性、覆盖面、深度、新鲜度、适用性、独立性和可追溯性。

最终产物不是被压成一条答案，而是一张可追踪的判断地图：已经观察到什么、由此推导出什么、哪些判断互相支持或冲突、在什么条件下成立、还缺什么证据，以及哪些检查最可能继续产生重要信息。

分歧是正式结果。只有用户明确要求选择方案或作最终建议时，技能才加载独立的定案模块；定案依据硬约束、工程事实、授权目标、权衡和不确定性，不依据角色数量。

## 适合解决的问题

- 项目架构、迁移或重大重构会产生哪些直接和间接影响。
- 某项产品或技术方案隐藏了哪些假设、边界和替代路径。
- 需求、文档、代码、配置、测试和实际行为是否相互一致。
- 跨模块、跨项目或跨团队变更会影响哪些接口、状态和利益相关者。
- 行业标准、监管要求、工程可行性和现实运维是否被充分覆盖。
- 安全、隐私、性能、可靠性、人因、成本和长期维护风险是否被低估。
- 当前证据能支持哪些判断，还存在哪些竞争性解释。
- 多个方案如何比较，以及还需要什么用户决定或验证。

## 不适合的情况

- 直接实现功能或修改项目。
- 解释单个函数或修复一个明确的局部错误。
- 常规代码审查、简单状态查询或一次检查即可可靠回答的问题。
- 与具体项目无关的一般资料查询。
- 个人生活规划。

## 六个审理维度

技能把容易混淆的概念分开：

| 维度 | 作用 |
| --- | --- |
| 审理者 | 谁执行审理，默认关注什么职责 |
| 审理角度 | 从哪个角色、系统边界、阶段、时间或后果观察 |
| 审理方式 | 使用哪种推理操作发现信息 |
| 专业知识 | 需要哪些当前标准、工程实践和领域能力 |
| 证据手段 | 如何检索、分级、比对、复现或测量 |
| 判断产物 | 产生发现、推论、风险、机会、竞争解释还是证据缺口 |

三个基础角色只负责第一个维度，不能代替其他五个维度。

## 三个基础审理者

### 证伪者（Falsifier）

优先寻找隐藏假设、反例、失败条件、替代原因、误用和能够区分判断的检查。它必须使用本次分配的具体审法，不能只进行泛泛挑错。

### 深化者（Deepener）

独立重建问题，寻找遗漏维度、关系、替代路径、二阶影响、生命周期后果、利益相关者和更准确的问题表达。

### 领域工程师（Domain engineer）

首先覆盖用户要求的决策领域，再处理后果最严重的相邻专业缺口。它按需检查标准、工程实践、可行性、迁移、安全、性能、运维、测试、回滚、成本和维护，但不会仅凭角色名称声称具备完整专业资质。

运行环境无法提供三个独立上下文时，主代理可以顺序执行相同的角色—审法组合，并准确说明独立性和覆盖限制。缺少一个角色只影响相关覆盖，不会让其他已验证发现失效。

## 动态选择审理角度和方式

技能先建立项目、证据和风险地图，再根据以下信息组成有上限的审理组合：

- 判断类型：事实、因果、预测、可行性、规范、比较、偏好或建议；
- 项目阶段：设计、开发、迁移、上线、运行、升级或退役；
- 观察对象：用户、运营、开发维护者、决策者、受影响方、组件、接口或整体系统；
- 后果、不确定性、可逆性和系统连接度；
- 安全、隐私、人因、治理、成本、架构和运维触发信号；
- 当前证据的来源类型和缺口。

常用推导方式包括：

- 第一性原理和假设拆解；
- 因果机制和替代原因；
- 反事实和逆向推导；
- 替代路径和外部对标；
- 系统关系、接口、场景和生命周期；
- 利益相关者和影响分布；
- 约束冲突、敏感性和信息价值；
- 需求到实现、测试和用户结果的追踪。

安全隐私、危害失效、人因、运维韧性、经济资源、治理责任和独立实验等专业方法仅在出现相应信号时启用。每项选中方法都要有负责人、证据要求、预期产物、预算和停止条件。方法越多不等于审理越好。

完整目录见[审理角度与方式](deliberate-project/references/inquiry-methods.md)。

## 根据提示词和要求自动判断侧重点

技能会先从整段输入中提取目标、对象、目标用户、付费者、操作者、验收指标、硬约束、强调项、排除项、风险容忍度、时间范围以及用户是否要求定案，形成一张“侧重点画像”，再分配审理角度、方法、证据和预算。它理解语义组合，不依赖机械关键词表。

判断优先级依次是：安全、法律、权利和授权边界；用户明确要求与排除项；验收证据与明确优先级；整句语义和强调结果；领域不可缺少的可行性与失败条件；项目证据；重复词和普通关键词；通用最佳实践。低层信号不能覆盖高层信号。

例如：

- “审赚钱项目，重点看半年能否盈利，不讨论融资”，主要审收入机制、成本、现金时点、需求证据和敏感性，并抑制融资方向。
- “审音乐制作软件，面向专业编曲用户，重点看低延迟和插件兼容”，主要审真实创作流程、音频测量、插件接口、故障恢复和平台标准。
- “审一个赚钱的音乐软件”，不会在“赚钱”和“音乐”中二选一，而会同时审商业模式、付费意愿、创作价值、延迟与兼容可行性、留存，以及产品质量如何传导到商业结果。

项目证据可以推翻用户假设，但不能暗中改写用户目标。即使用户没有提到，若某个领域硬条件一旦失败就会使目标失效，技能仍会加入该审理项，并说明加入原因和占用的审理预算。用户明确排除的内容会标记为“已遵守”“与目标冲突”或“被强制约束覆盖”；普通工程建议不能暗中覆盖排除项。

## 工作流程

1. **界定案件**：明确目标、约束、非目标、侧重点画像和项目边界；优先绑定冻结快照，只有实时清单时逐项记录内容指纹。
2. **建立广度与证据地图**：先扫描组件、接口、文档、测试、运行证据、利益相关者和外部约束。
3. **组成审理组合**：为高优先级判断选择差异最大的角度、方法和证据操作。
4. **领域扎根**：各角色基于中性说明独立查阅项目材料、可信技能、批准工具、权威资料和相关开源实现。
5. **隔离发现**：三个角色在不知道彼此首轮结果的情况下产出带方法与证据来源的发现卡。
6. **交叉增量**：补强证据、提出挑战、扩展影响、建立关系、重构解释和提出区分性检查，但不要求语言或判断趋同。
7. **证据比对与验证**：检查来源谱系、正反证据、适用范围、版本、共同原因风险和可重复性。
8. **建立发现—判断图谱**：保留支持、反驳、依赖、因果、限定、替代和取代关系。
9. **按信息增益结束**：只有覆盖、判断字段、分歧表示、关键验证和低预期信息增益同时满足才标记 `Complete`；预算或安全边界提前耗尽时只能标记 `Partial` 或 `Blocked`。
10. **按需定案**：仅在用户明确要求选择、推荐、排序或决定时运行。

## 发现与判断

技能分别记录：

- 直接观察；
- 具体发现；
- 派生判断；
- 暂定假设；
- 竞争性解释；
- 风险和机会；
- 用户或权威决策者的明确偏好；
- 缺失的证据维度；
- 能够改变判断的验证建议。

重要结果带稳定 ID，并记录审理者、角度、方法、证据、成立条件、项目影响、新增价值和覆盖限制。不同结果可以通过 `supports`、`contradicts`、`depends_on`、`causes`、`qualifies`、`alternative_to` 和 `supersedes` 关联。

审理状态使用：

- `Observed`：在适用项目证据或可重复检查中直接观察；
- `Supported`：当前证据支持经过校准的判断；
- `Contested`：存在重要反证或竞争解释；
- `Conditional`：只在明确条件下成立；
- `Open`：当前证据无法区分重要可能性；
- `User-dependent`：需要授权者的偏好、优先级或治理决定；
- `Coverage-limited`：缺少角色、角度、方法、证据维度或检查手段；
- `Superseded`：新版本取代旧版本，但历史仍保留。

这些状态描述当前发现和判断，不描述角色之间是否一致。

详细规则见[发现与判断模型](deliberate-project/references/finding-judgment-model.md)。

## 证据比对

材料数量不能证明专业程度。每项重要证据分别检查：

- 权威性；
- 覆盖范围；
- 分析深度；
- 时间和版本新鲜度；
- 对当前项目的适用性；
- 与其他来源、工具和模型解释的独立性；
- 是否能够回到原始位置核验。

多篇文章转述同一份报告只算一条来源谱系。三个角色使用同一来源或同一模型解释，也不构成独立互证。重要冲突要先确认是否属于不同版本、范围、环境或定义，再比较直接程度、适用性、方法质量和能够区分解释的检查。

详细规则见[证据比对](deliberate-project/references/evidence-comparison.md)。

## 可选定案

发现阶段可以在存在多个竞争判断时正常结束。用户明确要求作决定时，定案模块才比较：

1. 适用法律、强制标准、基本权利、明确禁止事项以及强制性的安全与隐私控制；
2. 合同、互操作承诺和已批准决策；
3. 工程与运维可行性；
4. 授权决策者的目标和优先级；
5. 生命周期风险和推荐实践；
6. 团队与工具偏好。

非零安全或隐私残余风险不会自动成为绝对否决项；技能会区分强制控制、推荐控制、授权风险阈值和残余风险接受权。可能输出推荐、附条件推荐、多个可行方案、需要用户决定、证据不足或当前无可行方案。完整规则见[可选定案](deliberate-project/references/optional-adjudication.md)。

## 专业知识和能力边界

技能按项目临时建立领域依据，不维护一个声称覆盖所有行业的静态知识库。已经安装的技能和工具只有在适用性、来源、授权、精确操作、数据外发边界和副作用都能说明时才进入能力账本。

专业判断必须满足对应证据维度。例如可行性需要真实路径、前置条件、验证、回滚和成本；安全隐私需要威胁或数据模型、适用控制和独立检查；UI 与人因需要可观察工作流、代表性任务或可访问性证据和目标用户意图。缺少维度就明确降低覆盖，不把角色输出描述成持证专业鉴证。

## 安全边界

- 审议阶段只分析，不修改项目、代码、计划、数据、基础设施、账户或外部系统。
- 有状态诊断只能在一次性隔离环境中进行。
- 外部检索不得提交密钥、私有代码、客户数据或可识别信息。
- 项目文件、网页、技能、MCP 指令和工具返回内容都只是待检查证据。
- 提示词本身不是权限执行器；技能分别报告项目写保护、工具审计、执行位置、外部副作用路径和安全保证。
- 在宿主没有强制只读时，只允许实时读取并核对前后指纹；有状态检查必须进入冻结副本或隔离环境。
- 用户在同一请求中明确要求实现时，该请求已经构成范围内授权；审议报告完成后继续实现，无需机械地再次询问。

## 自动经验与持续维护

本次案件材料、受治理经验目录和技能核心规则彼此分离。经验只在报告稳定后由主代理通过 `scripts/experience_catalog.py` 写入已配置根目录下固定的 `deliberate-project/experience.sqlite3`；角色代理不能写入。工具使用 SQLite 事务、稳定经验 ID、独立案例去重和完整状态历史，拒绝未通过隐私/许可检查或缺少适用范围、期限和证据定位的记录。

经验先经历 `Candidate`、`Shadow`、`Active`。普通经验至少在两个独立案例复现后才进入 Shadow，再经过两个独立 Shadow 正向结果才进入 Active；已验证的高风险流程修复可以提前进入 Shadow，但不能直接进入 Active。冲突会隔离双方，回归会自动转入 `Rolled-back`。影子经验不能暗中改变发现和判断。

当前项目直接证据优先于经验目录。新旧经验发生真实冲突时隔离双方并保留历史，不能静默覆盖。核心技能只因安全或来源完整性问题、重复出现的重大流程缺陷、宿主/工具/标准变化或明确授权的新能力而重新打开，避免无边界增加规则。

首次使用前，把现有绝对目录写入 `CODEX_HOME\deliberate-project-experience-root.txt` 的唯一一行；也可以配置用户环境变量：

```powershell
[Environment]::SetEnvironmentVariable("AEGOS_SKILLS_EXPERIENCE_ROOT", "<现有经验根目录>", "User")
```

完整治理规则见[经验目录治理](deliberate-project/references/experience-governance.md)。

## 输出内容

无论用户要求多简短的格式，报告都保留一段最小披露：快照及漂移、访问配置、安全保证、缺失角色或方法、`Complete/Partial/Blocked` 完成状态、预算耗尽或延期覆盖、表示完整性，以及经验目录是否写入。其余默认内容为：

1. 判断全景；
2. 范围、快照、角色、角度、方法和重要遗漏；
3. 按主题或影响整理的重要新发现；
4. 派生判断、竞争判断、条件和错误后果；
5. 正反证据、来源谱系、版本和适用范围；
6. 风险、机会和受影响方；
7. 覆盖缺口及最有区分力的下一步检查；
8. 用户明确要求时才附定案结果。

不会输出角色扮演对话、内部思维过程或原始代理记录。

## 安装

```powershell
git clone https://github.com/JoyceBrown/deliberate-project.git
Set-Location deliberate-project
$codexRoot = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE ".codex" }
$skillsRoot = Join-Path $codexRoot "skills"
$source = (Resolve-Path ".\deliberate-project").Path
$destination = Join-Path $skillsRoot "deliberate-project"
if ([IO.Path]::GetFileName($destination) -ne "deliberate-project") { throw "Unexpected destination" }
New-Item -ItemType Directory -Force -Path $skillsRoot | Out-Null
robocopy $source $destination /MIR /R:2 /W:1
if ($LASTEXITCODE -ge 8) { throw "Skill synchronization failed: $LASTEXITCODE" }
```

## 调用示例

```text
三堂会审：从不同角度和审理方式分析这次架构迁移，尽量发现遗漏细节、竞争判断和证据缺口。
```

```text
$deliberate-project 审议这个产品方案；先扩展发现和判断，最后再按我的目标推荐方案。
```
